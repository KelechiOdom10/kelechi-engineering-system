# Research

The deliverable is a decision supported by inspectable evidence. Default to read-only research; a recommendation does not authorize implementation or publication.

1. Read the request, repository rules, relevant code and prior decisions. Check installed versions and source dates before relying on old notes. State the goal, what must remain true, what may change, actual consumers and target environment. Reconcile named requested deliverables and earlier commitments; do not substitute a useful prerequisite for the requested outcome.
2. Use [the decision record](../../templates/research-decision.md). Set criteria before selecting a favorite. Include keeping the current approach or removing the mechanism. Name the benefit, maintenance cost, unknowns and time/tool budget. Ask only for a consequential preference or authority decision that evidence cannot settle.
3. Split genuinely independent questions when delegation is permitted: current implementation, external primary sources, real usage or domain behavior, and the strongest case against the favorite. Follow the active host's agent limits and completion events; do not import another harness's commands, models or polling. For a small question, work inline. Give each researcher the same constraints, exact versions, focused questions, output limit and read/write boundary.
4. Read implementations and contracts behind articles. Separate sourced facts, measured observations and inferences. Record environment, baseline and method for measurements. Missing evidence remains unknown; citation count, novelty and model agreement are not proof. Before declaring something absent, search plausible names and locations at the relevant revision.
5. Resolve consequential disagreements with the smallest allowed probe. Calibrate against a known result or unchanged control. Measure the claimed benefit and likely regression in the real consumer; a standalone fixture is a scoped hint when integration differs. After repeated failed approaches, reassess the premise and budget instead of adding another patch.
6. For visual alternatives, use `create-canvas` to preserve the approved baseline and distinct concepts with the same content and dimensions. Use `ui-sweep` for actual state coverage. A screenshot does not prove motion, a mock does not prove the real integration, and research does not change an agreed product requirement.
7. Return the decision, decisive evidence, alternatives, constraints checked, uncertainty and smallest next action. Link actual artifacts and distinguish completed, partial and blocked deliverables. Only independently verified lessons become durable guidance. Use [the editable frontier](../../docs/research-loop.md) when further cycles are useful; keep goal, authority and stopping conditions fixed.

Adapted from [dmytro's research](https://pqoqubbw.dev/skills/research), using repository adapters and host-native orchestration instead of fixed fan-out or workflow commands.
